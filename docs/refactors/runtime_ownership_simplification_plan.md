# Runtime Ownership Simplification Plan

- Goal: make every runtime dumb at the boundary it does not own.
- Goal: delete duplicate interpretation paths instead of wrapping them with more facades.
- Goal: keep Electron as the host shell, the SDK as the reusable runtime, the sidecar as the local executor/store, and the backend as the hosted model loop and policy owner.
- Goal: make failed contracts visible in tests before they reach `bin/windie start desktop`.

## Issues, Implementation, and Success Criteria

- Issue: query identity is currently split between SDK `turnRef`, renderer optimistic message IDs, Electron `queryMessageId`, and backend websocket message IDs. `DesktopLiveTurnRuntimeClient` creates an SDK runtime, `ConversationRuntime.send()` adds `turn_ref` to the query payload, `desktopBackendTransport.ts` forwards `turn_ref` through `send-chat-query`, and `ipc.cjs`/`ipc_query_send_runtime.cjs` generate another `queryMessageId`. The backend `QueryPayload` forbids extra fields, so `query.payload.turn_ref` can be rejected even though `turn_ref` is valid as stream context.
  - Implement: make the websocket envelope id the only backend turn id for desktop query transport. Extend the SDK `BackendTransport` query API so `ConversationRuntime.send()` can pass its `turnRef` as the outgoing message id without adding `turn_ref` to `QueryPayload`. Strip or forbid `turn_ref` at the renderer-to-main query IPC boundary. Keep renderer optimistic user row identity separate from backend turn identity unless it is explicitly passed as the SDK turn id.
  - Success criteria: backend `QueryPayload` receives only fields allowed by `backend/src/api/schemas/incoming.py`; backend stream events still return `turn_ref` equal to the websocket message id; `DesktopBackendTransport`, `DesktopLiveTurnRuntimeClient`, `IpcQueryRuntime`, and backend schema/compatibility tests fail if `turn_ref` reappears inside `query.payload`; sending a chat from the dashboard no longer produces `Invalid message format: query.payload.turn_ref`.

- Issue: query payload construction is duplicated across renderer, Electron main, SDK transport, and backend schema. Renderer shapes screenshots, readable files, workspace binding, model sync, memory preference, and transcript writes in `useChatMessageSender.ts`; `desktopBackendTransport.ts` reshapes that into snake_case; Electron main reshapes again, adds local user broadcast, system state, memory, repo instructions, and agent definition context; backend validates a different final contract.
  - Implement: create one desktop query command contract in the SDK or SDK-facing desktop runtime, with a strict `DesktopQueryInput` for renderer callers and a separate backend-safe `BackendQueryPayload` for websocket transport. Renderer should supply user intent and UI-local attachment choices only. Electron main should own host-only enrichment such as system state, display affinity, repo instructions, and overlay pre-capture. The SDK transport should own conversion to backend websocket command shape and should reject fields that do not belong in backend payloads.
  - Success criteria: there is one tested function that maps desktop query input to backend query payload; renderer feature code does not mention backend-only payload fields other than the facade input type; main query tests assert exact backend payload keys; adding a new query field requires changing one mapper and one contract test, not renderer, main, and SDK fallbacks.

- Issue: `frontend/src/main/ipc.cjs` remains a high-risk mixed owner. It registers unrelated IPC handlers, owns websocket connection state, settings sync, query send, overlay phase transitions, renderer event replay, backend event processing, SDK runtime construction, list-models queuing, transcript session sync, artifact fetch, config save, OAuth, renderer logs, and test-only helpers in one 1300+ line file.
  - Implement: turn `ipc.cjs` into a composition root only. Move query send orchestration into a focused desktop query runtime, backend websocket/session lifecycle into a backend session runtime, settings/model command routing into a settings runtime, renderer event broadcasting/replay into an event fanout runtime, and diagnostics/log forwarding into a diagnostics runtime. Keep only dependency wiring and handler registration in `ipc.cjs`.
  - Success criteria: `ipc.cjs` no longer contains query payload construction, backend event semantic handling, settings sync policy, or model-list queuing logic inline; focused modules have unit tests for their own state machines; the composition root can be skimmed without understanding query, settings, tool, and overlay internals at once.

- Issue: live turn projection is SDK-branded but not fully SDK-owned. Electron main currently calls `createCurrentTurnProjector().applyBackendEvent(rawBackendEvent)` directly in `windie_sdk_runtime.cjs`, then separately calls `normalizeBackendEventToConversationEvent()`. That creates two reductions from raw backend events before renderer sees `conversation-runtime-updated` and `conversation-event`.
  - Implement: reduce raw backend events into normalized SDK conversation events once, then derive `currentTurn` from the normalized conversation runtime state. Electron main should subscribe to or request SDK `ConversationSnapshot` updates and forward that typed snapshot to renderer. The raw backend projector can stay only as a test helper or be deleted after the normalized path covers current-turn behavior.
  - Success criteria: `conversation-runtime-updated` is emitted from SDK snapshot state, not a parallel raw backend projector; SDK tests prove assistant text, reasoning text, tool calls, tool outputs, completion, and error phase are reduced from the same normalized events used for display and rehydrate; renderer dashboard and response overlay render the same `currentTurn` object.

- Issue: renderer still owns too much stream meaning. `useConversationRuntimeProjectionStream.ts` consumes `currentTurn`, but `useChatStream.ts` and its handlers still interpret many SDK-normalized events for transcript, metadata, completion, errors, token usage, memory, compaction, tool calls, and local user events. Some of this is necessary side effect handling, but the boundary is not obvious and can drift back into live-row ownership.
  - Implement: split renderer stream handling into two explicit consumers: a live projection consumer that only stores and renders SDK `currentTurn`, and a side-effect consumer that only persists transcript/metadata/telemetry events. Delete live assistant/tool/phase mutation from side-effect handlers. Move any event-to-display-row shaping still needed by both dashboard and overlay into SDK projection helpers or a single renderer display adapter fed by SDK projection.
  - Success criteria: no renderer code builds active assistant/tool rows from `conversation-event` or `from-backend`; `useChatStream` cannot set active live response text, tool phase, or response overlay content; transcript side-effect tests still prove rows are persisted; live UI tests prove dashboard and response overlay stay identical for the same `currentTurn`.

- Issue: raw `from-backend` still has legitimate non-chat consumers, but it is also a temptation path for chat semantics. App config/status, audio chunks, agent settings manifest state, and compatibility traffic use `FROM_BACKEND`; chat live state is supposed to use SDK projection and SDK conversation events.
  - Implement: classify every `FROM_BACKEND` renderer subscription as either non-chat side channel, diagnostics, or migration debt. Move model/settings events to a typed settings channel, tool manifest/catalog events to an agent capability channel, and audio chunks to an audio channel. Leave `from-backend` only for compatibility diagnostics or remove it for chat windows after typed channels are complete.
  - Success criteria: searching renderer code for `ON_CHANNELS.FROM_BACKEND` shows no chat stream or chat live-state consumer; each remaining subscription has a named owner and typed payload test; model/settings UI does not depend on raw backend stream traffic for normal startup.

- Issue: settings and model list ownership is still spread across `AppConfigProvider.jsx`, `DesktopSettingsRuntimeClient`, `desktopBackendTransport.ts`, main `to-backend` routing, initial settings sync gates, and backend settings/model handlers. This caused startup model-list behavior to depend on hidden connection timing.
  - Implement: create one desktop settings/model runtime with explicit states: local config loaded, backend connected, settings synced, model catalog requested, model catalog received, sync error. App config should be a dumb React store over that runtime state. Model list requests should be idempotent commands owned by the settings runtime, not provider mount effects plus main-process queue special cases.
  - Success criteria: dashboard startup always requests models through the settings runtime once per app session or explicit refresh; `AppConfigProvider` has no raw backend event subscription and no direct model-list connection policy; tests cover cold start, backend reconnect, config load from disk, model-list failure, and settings-update acknowledgement.

- Issue: conversation authority is still hard to reason about. The docs say SDK plus sidecar store own conversation events/projections, but renderer state also tracks `activeConversationRef`, transcript session state, conversation inference hydration state, workspace binding, pending transcript writes, and current-turn projection. These may be caches, but the code does not always make cache versus authority clear.
  - Implement: define a single desktop conversation session service as the only mutator for active conversation identity, user binding, backend rehydrate state, and workspace binding. Renderer stores should read session snapshots and render projections, not independently decide active conversation or backend hydration status. Keep sidecar storage behind `SidecarConversationStore` and make desktop adapters write enrichment only.
  - Success criteria: all active conversation mutations route through one service; `chatStore.activeConversationRef` is set only from that service or a single adapter; opening a past chat, starting a new chat, sending from the pill, and receiving late events all have tests proving events do not jump conversations.

- Issue: conversation persistence has a canonical SDK store, but renderer infrastructure still has multiple transcript projections and adapters that can look like parallel stores: `desktopConversationStore.ts`, `sdkSidecarConversationStore.ts`, local transcript helpers, pending transcript queues, display projection conversion, and sidecar chat-event RPCs.
  - Implement: keep `SidecarConversationStore` as the canonical event store interface and collapse desktop-specific persistence helpers into either store host write params or clearly named UI projection adapters. Delete any adapter that parses stored transcript rows into SDK events when the SDK store can load normalized events directly. Keep pending writes as a transport reliability layer only.
  - Success criteria: display and rehydrate projections are generated by SDK projection builders from SDK events; desktop adapters do not own message/tool interpretation tables; sidecar tests prove stored rows preserve revision, message index, turn id, tool ids, artifact refs, and workspace binding; renderer tests prove dashboard replay and backend rehydrate use the same projection source.

- Issue: tool execution routing is mostly SDK-owned now, but the code still has historical execution surfaces: SDK `ToolExecutionCoordinator`, Electron main SDK runtime callbacks, `local_backend_bridge_execute_tool_runtime.cjs`, sidecar daemon `/execute-tool`, JSON-RPC fallback, executable tool registry, and old wrapper artifact references. The boundaries are valid, but ownership must be explicit to avoid adding renderer or main-process routing semantics again.
  - Implement: keep the SDK as the only owner of local-tool claim, request/bundle correlation, post-action screenshot policy, result delivery, and display-only tool-output projection. Keep Electron main as a host adapter that calls sidecar execution and supplies screenshots/display affinity. Keep sidecar as the direct executable registry. Delete or quarantine any legacy renderer execute-tool path and non-live wrapper tool names.
  - Success criteria: renderer has no local tool execution IPC path; Electron main does not decide whether a backend tool event is claimed beyond providing host callbacks; missing `request_id` or `bundle_id` creates an SDK runtime error and does not invoke sidecar; tool tests cover single call, bundle, local execution failure, backend delivery failure, post-action screenshot, and sidecar missing-tool errors.

- Issue: sidecar bridge ownership is still dense. `local_backend_bridge.cjs` supervises process lifecycle, readiness, stdout JSON parsing, daemon launch, RPC registration, sidecar events, scoped host IPC, execute-tool runtime, status broadcasts, and adapter exports. Some split modules exist, but the bridge remains a second composition root with substantial behavior.
  - Implement: split sidecar bridge into process supervisor wiring, daemon client lifecycle, JSON-RPC transport, RPC handler registry, local tool host adapter, and status broadcaster. Keep camelCase-to-snake_case in one mapper registry. Make adding a sidecar RPC require one handler definition, one typed mapper, and one sidecar test.
  - Success criteria: `local_backend_bridge.cjs` no longer owns stdout parsing loops and execute-tool policy inline; readiness state has one owner; sidecar daemon and legacy process fallback share the same request transport interface; mapper tests fail when a field alias is added outside the mapper registry.

- Issue: backend/frontend websocket contracts are enforced too late. The backend schema correctly forbids unknown query fields, but frontend tests currently allow or expect payload fields that the backend rejects. The failure is caught only by a live backend error.
  - Implement: add contract tests that validate frontend websocket payload builders against backend-owned JSON schema fixtures or generated schema snapshots, without importing backend Python code into frontend runtime. Generate or export schema artifacts in tests only, then assert query, stop, rehydrate, settings, list-models, tool-result, and bundle-result payloads are exact.
  - Success criteria: CI fails before runtime if frontend sends an extra backend payload key; frontend tests no longer expect invalid `turn_ref` inside query payload; backend tests still own Pydantic validation; docs state which fields live in websocket envelope context versus query payload.

- Issue: diagnostics are useful but not cleanly owned. Interaction logs now flow from renderer to main and may include message text when requested for debugging. Without one diagnostics boundary, future logging can leak user data or become impossible to disable.
  - Implement: create a diagnostics runtime with explicit dev/diagnostic gating, event schemas, message-content logging policy, and redaction options. Renderer should call one interaction logger; main should forward or print through one diagnostics sink. Production builds should have a tested default that excludes message content unless an explicit diagnostic flag is enabled.
  - Success criteria: all frontend interaction logs use one schema; `messageText` logging is controlled by an explicit flag or dev-only policy; tests prove production redaction; no feature component writes ad hoc user interaction logs directly to `console`.

- Issue: docs already describe the desired SDK-first architecture, but some docs now read more complete than the code. This creates false confidence when a bug is caused by remaining migration debt.
  - Implement: update architecture docs to distinguish "current behavior", "target behavior", and "known migration debt" for query send, live turn projection, raw backend events, settings/model sync, and conversation storage. Keep this refactor plan as the deletion checklist and link specific completed changes back to it.
  - Success criteria: docs do not imply raw backend event interpretation is gone until searches and tests prove it; every remaining duplicate path has an owner, deletion condition, and test target; `bin/windie docs list` passes after each related change.

## Do Not Implement

- Do not add another renderer facade that wraps the old renderer-to-main-to-SDK-to-main path without deleting an old path.
- Do not make frontend or sidecar import backend Python code for runtime behavior or schema parity.
- Do not let Electron main own assistant text, reasoning text, tool-card content, model-facing tool policy, provider history, or backend session semantics.
- Do not let renderer components parse backend raw events for live assistant/tool state after SDK projection is available.
- Do not accept both camelCase and snake_case deep inside feature code; normalize aliases once at runtime boundaries.
- Do not keep compatibility shims unless a test or external client proves they are still needed.
