# IPC Message Protocol Documentation

## 1. Overview

This document defines the communication protocol between the Electron frontend and the Python backend. All communication happens over a WebSocket connection, allowing for real-time, bidirectional message passing.

The architecture is designed to be simple and extensible, enabling new features to be added with minimal changes to the core infrastructure.

---

## 2. Connection

- **URL**: `ws://localhost:8765`
- **Protocol**: WebSocket (`ws`)

The Electron main process (`frontend/src/main/ipc.js`) is responsible for establishing and maintaining the connection. It includes automatic reconnection logic to handle cases where the backend server is not yet running or restarts.

---

## 3. Message Structure

All messages exchanged between the frontend and backend **must** be in JSON format and adhere to the following structure.

### Frontend -> Backend Message

```json
{
  "id": "string (UUIDv4)",
  "type": "string",
  "payload": "object",
  "timestamp": "string (ISO 8601)"
}
```

- **`id`**: A unique identifier (UUIDv4) for the message, generated by the client. This helps in tracking requests and pairing them with responses.
- **`type`**: A string that defines the purpose of the message (e.g., `"ping"`, `"execute_command"`). This is used for routing the message to the correct handler on the backend.
- **`payload`**: A JSON object containing the data relevant to the message type.
- **`timestamp`**: An ISO 8601 timestamp indicating when the message was sent.

### Backend -> Frontend Message

The backend uses the same structure for messages it sends to the frontend.

```json
{
  "id": "string (UUIDv4, matches original request)",
  "type": "string",
  "payload": "object"
}
```

- **`id`**: When replying to a specific request, the backend **should** use the same `id` as the original message. For push notifications not tied to a request, a new `id` can be generated.
- **`type`**: The type of the response message (e.g., `"pong"`, `"command_result"`).
- **`payload`**: A JSON object containing the response data.

## 4. Defined Message Types (Initial)

### `ping`

- **Direction**: Frontend -> Backend
- **Purpose**: A simple keep-alive or connection test message.
- **Payload**: Can be any object, but a simple string is sufficient.
- **Example**:
  ```json
  {
    "id": "a1b2c3d4-e5f6-7890-1234-567890abcdef",
    "type": "ping",
    "payload": "Hello from React!",
    "timestamp": "2025-10-22T10:00:00Z"
  }
  ```

### `pong`

- **Direction**: Backend -> Frontend
- **Purpose**: The direct response to a `ping` message.
- **Payload**: A confirmation message from the backend.
- **Example**:
  ```json
  {
    "id": "a1b2c3d4-e5f6-7890-1234-567890abcdef",
    "type": "pong",
    "payload": "Hello from Python!"
  }
  ```

### `error`

- **Direction**: Backend -> Frontend
- **Purpose**: Sent by the backend when it encounters an error, such as receiving malformed JSON or failing to process a valid message.
- **Payload**: An object containing an error message.
- **Example**:
  ```json
  {
    "id": null,
    "type": "error",
    "payload": {
      "message": "Malformed JSON received."
    }
  }
  ```

## 5. How to Add a New Message Type (Example)

This section provides a clear guide for contributors on how to extend the IPC protocol.

**Goal**: Add a new feature to get the current operating system from the backend.

### Step 1: Define the New Message Type

- **Request Type**: `get_os_info`
- **Response Type**: `os_info_result`

### Step 2: Send the Message from the Frontend

In the React component (e.g., `App.jsx`), create a function to send the new message.

```javascript
// In a React component
function getOperatingSystem() {
  window.ipc.send('to-backend', {
    type: 'get_os_info',
    payload: {}, // No payload needed for this request
  });
}
```

### Step 3: Handle the Message in the Backend

In `backend/server.py`, update the `handler` function to recognize and process the `get_os_info` type.

```python
# In backend/server.py, inside the handler's `try...except` block
import platform # Add this import at the top

# ... inside the async for loop ...
data = json.loads(message)
logger.info("Received message: %s", data)

if data.get("type") == "ping":
    # ... (ping logic) ...

elif data.get("type") == "get_os_info":
    response = {
        "type": "os_info_result",
        "id": data.get("id"),
        "payload": {
            "system": platform.system(),
            "release": platform.release(),
        }
    }
    await websocket.send(json.dumps(response))
    logger.info("Sent os_info_result to %s", websocket.remote_address)

```

### Step 4: Receive the Response in the Frontend

In the React component, add a listener to handle the `os_info_result` message from the backend.

```javascript
// In the useEffect hook of a React component
useEffect(() => {
  const removeListener = window.ipc.on('from-backend', (data) => {
    if (data.type === 'os_info_result') {
      console.log('OS Info:', data.payload);
      // Update state with the OS info
    } else if (data.type === 'pong') {
      // ... (handle pong) ...
    }
  });

  return () => removeListener();
}, []);
```

By following this pattern, contributors can easily add new functionality without altering the core communication logic.
