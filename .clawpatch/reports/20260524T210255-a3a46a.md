## low: Repeated override refreshes stack provider overrides without cleanup

id: fnd_sig-feat-library-41e7c46fe2-c00c_dee3f653c8
category: performance
confidence: medium
triage: risk
status: open
feature: Python source backend/src/core/container/:api (feat_library_41e7c46fe2)

evidence:
- backend/src/core/container/api_runtime.py:30-35 (ApiRuntimeBinder.refresh_overrides)
- backend/src/core/container/api_runtime.py:43-53 (ApiRuntimeBinder._sync_api_container_overrides)

Each refresh call applies new provider overrides to config, config_service, model_service, and session_manager. dependency_injector provider overrides are stacked unless reset, so repeated refresh_overrides calls can leave an unbounded chain of stale Object providers attached to each dependency provider. Besides memory growth, later reset behavior becomes surprising because old overrides remain underneath the newest one.

recommendation:
Before applying replacement overrides, reset the existing overrides for these dependency providers or replace the ApiContainer wholesale. If stacking is intentional, document the lifecycle and expose a cleanup path.

test analysis:
No linked tests were included, and there is no evidence of a test that calls refresh_overrides repeatedly and inspects provider override depth or cleanup behavior.

suggested regression test:
Call refresh_overrides multiple times after creating the ApiContainer and assert each dependency provider has only the expected active override after refresh.

minimum fix scope:
ApiRuntimeBinder._sync_api_container_overrides and a focused lifecycle regression test.

## low: Returned artifact URL is built from the incoming request base URL

id: fnd_sig-feat-route-486a6ec0f4-c39696_c30622d862
category: security
confidence: medium
triage: risk
status: open
feature: FastAPI route POST /api/artifacts/ (feat_route_486a6ec0f4)

evidence:
- backend/src/api/routes/artifacts/router.py:36-43 (upload_artifact)

The upload response constructs the artifact URL directly from request.base_url. In common ASGI deployments, that value can depend on Host or forwarded headers unless separately constrained by trusted-host/proxy middleware. A malicious or misconfigured inbound host can therefore cause the API to return an attacker-chosen absolute artifact URL, which is risky if clients persist, display, or later fetch the returned URL as authoritative.

recommendation:
Build artifact URLs from a configured public base URL, or return a relative path such as /api/artifacts/{artifact_id}. If request-derived hosts are required, ensure trusted host/proxy middleware is enforced and add a test for the expected base URL behavior.

test analysis:
No linked tests were included for response URL construction, and the handler has no local guard showing the request host has been validated.

suggested regression test:
Add a route test that sends a forged Host header and asserts the returned url uses the configured public base URL or remains relative.

minimum fix scope:
backend/src/api/routes/artifacts/router.py and configuration/test coverage for artifact URL generation.

repro:
POST /api/artifacts/ with a forged Host header in a deployment that does not enforce trusted hosts; the response url field will use that host.
