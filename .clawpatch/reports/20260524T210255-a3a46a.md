## low: Test shutdown leaves authentication and config state behind

id: fnd_sig-feat-library-cd310e97cf-534b_d11316188a
category: test-gap
confidence: medium
triage: test-gap
status: open
feature: Node source frontend/src/main/:ipc (feat_library_cd310e97cf)

evidence:
- frontend/src/main/ipc.cjs:131-155
- frontend/src/main/ipc.cjs:710-724

The IPC module keeps process-global state for install auth, user/session identity, active config, connection state, and runtime objects. The test shutdown helper resets the runtime, windows, observers, callbacks, and some pending state, but it does not clear currentUserId, currentInstallId, currentInstallToken, latestFrontendConfig, hasAttemptedInitialSettingsSync, or currentGlobalAgentStopShortcutStatus. Tests that initialize IPC after a prior authenticated/configured test can accidentally reuse stale auth headers or config values, masking regressions or making tests order-dependent.

recommendation:
Extend shutdownIpcForTests to reset all process-global IPC state that can influence a subsequent initialization, especially install auth, frontend config, shortcut status, and first-query/settings flags. Keep the reset list close to the declarations so future globals are harder to miss.

test analysis:
No linked tests are included for this feature, and the existing shutdown helper itself is the only test isolation mechanism visible in the excerpt.

suggested regression test:
Add a Jest test that initializes IPC with auth/config state, calls shutdownIpcForTests, reinitializes, and asserts that subsequent handshakes/status payloads do not include the prior install token, user id, config, or shortcut status.

minimum fix scope:
frontend/src/main/ipc.cjs shutdownIpcForTests plus a focused frontend IPC test.

category: security
confidence: medium
triage: risk
status: open
feature: FastAPI route POST /api/embeddings/ (feat_route_f4997418a4)

evidence:
- backend/src/api/routes/memory/embeddings/router.py:118-121 (generate_embedding)
- backend/src/api/routes/memory/embeddings/router.py:40-44 (_log_embedding_route_start)
- backend/src/api/routes/memory/embeddings/router.py:82-89 (_log_embedding_route_failure)

The route accepts request.model_name from the network request and passes it directly into route log messages. If model_name can contain newlines or control characters, a caller can forge or obscure log entries, which matters because this route crosses network and user-input trust boundaries and logs both normal and failure paths.

recommendation:
Normalize model_name before logging, for example by replacing control characters/newlines, bounding length, or logging a validated canonical model identifier rather than the raw request field.

test analysis:
No tests are linked for this feature, and the excerpt contains no coverage asserting log-safe handling of untrusted request fields.

suggested regression test:
Add a route-level or helper-level test that passes a model_name containing a newline/control character and asserts the emitted log record contains only a sanitized single-line value.

minimum fix scope:
Sanitize or canonicalize request.model_name at the logging boundary in this router or in the logging helper functions.

## low: Visibility intent persistence can be lost after an interrupted write or corrupt JSON

id: fnd_sig-feat-library-d21c8fcd19-4b2b_d887201964
category: data-loss
confidence: medium
triage: risk
status: open
feature: Node source frontend/src/main/:chat (feat_library_d21c8fcd19)

evidence:
- frontend/src/main/chat_pill_visibility_intent_store.cjs:26-30 (readChatPillVisibilityIntent)
- frontend/src/main/chat_pill_visibility_intent_store.cjs:41-45 (writeChatPillVisibilityIntent)

The store writes the only persisted copy directly to the target JSON file and the reader treats any parse/read error as `{ userHidden: false }`. If the app exits, the process crashes, or the filesystem fails mid-write after truncation, the next startup silently interprets the corrupt or partial file as a visible chat pill. That loses the user's explicit hidden intent instead of preserving the prior value or failing closed for the persisted preference.

recommendation:
Write atomically through a temp file in the same directory followed by rename, and consider preserving the last known value or returning an error marker for corrupt state instead of silently resetting to visible.

test analysis:
No linked tests are included for this feature, and the shown package manifest only exposes generic Jest commands rather than a focused persistence/corruption regression.

suggested regression test:
Add a Jest test for the intent store that verifies writes are atomic or, at minimum, that corrupt existing state does not silently convert a previously hidden intent into visible without an explicit reset path.

minimum fix scope:
Update `writeChatPillVisibilityIntent` to use temp-file plus rename semantics and adjust `readChatPillVisibilityIntent` error handling/tests for corrupt persisted state.

repro:
Persist `{ userHidden: true }`, replace `chat-pill-visibility-intent.json` with a truncated JSON value such as `{ "userHidden": tru`, then call `readChatPillVisibilityIntent`; it returns `{ userHidden: false }`.
