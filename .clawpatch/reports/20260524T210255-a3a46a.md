## low: Upload response URL trusts request base URL

id: fnd_sig-feat-library-57e7672bcd-0756_4028497961
category: security
confidence: medium
triage: risk
status: open
feature: Python source backend/src/api/routes/artifacts (feat_library_57e7672bcd)

evidence:
- backend/src/api/routes/artifacts/router.py:36-43 (upload_artifact)

The upload response constructs the artifact URL from request.base_url. In common ASGI deployments this value is influenced by Host and forwarded headers unless separately constrained by trusted proxy configuration. A malicious or misconfigured Host header can therefore cause the API to return an attacker-controlled absolute artifact URL, which is a response poisoning/phishing risk and can break clients that persist or display the returned URL.

recommendation:
Build artifact URLs from a configured canonical backend/public base URL, or return a relative artifact path instead of an absolute URL. If proxy-derived hosts are required, enforce trusted host/proxy middleware and cover the expected behavior in tests.

test analysis:
No linked tests are included, and the visible response model only asserts a url field exists, not that it is derived from a trusted source.

suggested regression test:
Add a route test that sends a forged Host header during upload and asserts the returned url uses the configured canonical base URL or a relative /api/artifacts/{id} path.

minimum fix scope:
backend/src/api/routes/artifacts/router.py, configuration or API contract if a canonical base URL does not already exist, and focused backend route tests.

## low: Visibility intent persistence can be lost after an interrupted write or corrupt JSON

category: data-loss
confidence: medium
triage: risk
status: open
feature: Node source frontend/src/main/:chat (feat_library_d21c8fcd19)

evidence:
- frontend/src/main/chat_pill_visibility_intent_store.cjs:26-30 (readChatPillVisibilityIntent)
- frontend/src/main/chat_pill_visibility_intent_store.cjs:41-45 (writeChatPillVisibilityIntent)

The store writes the only persisted copy directly to the target JSON file and the reader treats any parse/read error as `{ userHidden: false }`. If the app exits, the process crashes, or the filesystem fails mid-write after truncation, the next startup silently interprets the corrupt or partial file as a visible chat pill. That loses the user's explicit hidden intent instead of preserving the prior value or failing closed for the persisted preference.

recommendation:
Write atomically through a temp file in the same directory followed by rename, and consider preserving the last known value or returning an error marker for corrupt state instead of silently resetting to visible.

test analysis:
No linked tests are included for this feature, and the shown package manifest only exposes generic Jest commands rather than a focused persistence/corruption regression.

suggested regression test:
Add a Jest test for the intent store that verifies writes are atomic or, at minimum, that corrupt existing state does not silently convert a previously hidden intent into visible without an explicit reset path.

minimum fix scope:
Update `writeChatPillVisibilityIntent` to use temp-file plus rename semantics and adjust `readChatPillVisibilityIntent` error handling/tests for corrupt persisted state.

repro:
Persist `{ userHidden: true }`, replace `chat-pill-visibility-intent.json` with a truncated JSON value such as `{ "userHidden": tru`, then call `readChatPillVisibilityIntent`; it returns `{ userHidden: false }`.
